## 选股与分仓接口补充（2026-09-24；建议，待确认）

为避免上层模块直接生成不可追溯的交易数量，建议把流程拆成三层：

1. **选股策略层**：输出候选信号，只表达选择对象、方向、生成时间和排序依据。
2. **分仓层**：结合当时账户快照、可用现金、可卖数量和分仓规则，输出预算/目标数量计划。
3. **订单转换层**：根据已确定的执行日期、阶段、触发价和费用预留，把计划转换为回测引擎可消费的 `Order`。

### 1. 选股策略最终返回值

建议正式契约为 `list[CandidateSignal]`，而不是 `list[str]`：

```python
@dataclass(frozen=True)
class CandidateSignal:
    signal_id: str
    ts_code: str
    generated_date: date
    side: Literal["BUY", "SELL"]
    rank: int | None = None
    score: Decimal | None = None
    reason: str = ""
```

选股策略只表达“选谁、方向、何时产生、为什么”，不返回最终买入股数、成交价或费用。

### 2. 分仓模块最终返回值

建议正式契约为 `AllocationPlan`，其中每个对象一条 `AllocationItem`：

```python
@dataclass(frozen=True)
class AllocationItem:
    plan_id: str
    signal_id: str
    ts_code: str
    side: Literal["BUY", "SELL"]
    generated_date: date
    trade_date: date
    phase: Literal["OPEN", "INTRADAY", "CLOSE"]
    budget: Decimal | None = None
    target_quantity: int | None = None

@dataclass(frozen=True)
class AllocationPlan:
    plan_id: str
    generated_date: date
    items: tuple[AllocationItem, ...]
    unallocated_cash: Decimal
```

分仓层返回的是预算计划，不是已成交结果。`BUY` 主要填写 `budget`，由订单转换层根据参考价、整手规则和费用预留计算数量；`SELL` 主要填写 `target_quantity`，最终仍受当时可卖数量限制。未分配余额保留在 `unallocated_cash` 中，无候选时返回空 `items`，不伪造计划。

现有 `stock_keep`、`position_managent`、`ultimate_distribute` 可以保留作为快速验证接口，但建议改变最终返回语义：

## 单标的集中度上限与额度顺延（2026-09-28；已确认并落地）

### 需求原文（用户）

> 需要你检查文件 portfolio，看看里面有没有限制每只个股占总资金比列的限制
> 总资产为分母，超限后余额需要顺延给后续候选，，现在实现吧

### 已确认口径

| 项 | 确认值 |
|---|---|
| 分母 | **总资产**（可用现金 + 持仓市值），不是可用现金 |
| 超限处理 | 被截断的额度**顺延**给尚未定量的后续候选 |
| 候选全部顶满后 | 剩余额度**留作可用现金**，不突破上限加仓 |
| 本次实验取值 | `max_single_weight = 0.5`（单标的不超过总资产 50%） |
| 手数取整偏差 | **一并修正**（原口径按最低佣金粗估每手费用，低价标的会少买 1 手） |

### 落地实现

配置键 `max_single_weight`（占可用现金的比例写法，换算后与「占总资产比例」等价）：

```text
生效上限 = 该对象允许占总资金比例 ÷ 可用现金占总资产比例 × 总资产 − 该对象当前市值
```

- 用「占现金比例」是为了与返回的 `proportion` 直接对照；两种写法数学等价。
- 候选本轮预算 = `min(等分剩余额度, 剩余预算, 生效上限)`，四舍五入到整手后买入。
- 买入后 `剩余预算 = 可用预算 − 已分配`，被上限砍掉的额度自然顺延给后面的候选。
- 全部候选定量后若仍有剩余，写入 `unallocated` 并留在可用现金。
- 已有持仓的对象按「已占市值 + 本次成本」合并计算上限；已满配时上限为 0，本次不再加仓。
- 未配置该键或值 ≤ 0 时，完全保持原有等分行为。

### 数学性质（重要，非缺陷）

折算预算与上限是**同一条约束的两种写法**。当现金占总资产比例为 `cr`、上限比例为 `w` 时，
每个候选的预算上限为 `w/cr × 总资产 − 已占市值`。因此：

- 现金占比越低，折算出的名义预算越大（`cr=0.05` 时可达可用现金的 80 倍），
  但实际买入仍被 `总资产 × w` 与可用现金双重卡住。
- 当 N 个候选全部顶到 `w` 后，最多只能占用 `N × w × 总资产`。
  例如 3 个候选、`w=0.15` 时最多约 45% 仓位，其余必须留作现金。
  **这是集中度上限的必然结果，不是分配失败。**

### 手数取整口径修正说明

原实现按「整手费用 = 每手成交额 × 费率，且不低于最低佣金」反推手数，
在「每手成交额 < 最低佣金 / 费率」时（本项目为每手 100 股、费率 0.0001，
即价格 < 5 元）会把最低佣金重复计入每手费用，导致少买 1 手。

现改为按预算净额精确取整：`手数 = floor((预算 / (1 + 费率) − 最低佣金) / 每手成交额)`，
与撮合层的实际收费口径一致。同一预算下低价标的可能比旧结果多 1 手，
因此 E05/E06/E07/E08 的历史结果与本次口径不同，跨实验对照时须注意。
