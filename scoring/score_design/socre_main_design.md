### 回答（2026-09-22，建议方案，待确认）

**建议不要先人工列一份“知名妖股名单”，而是先识别历史上出现过的异常强势区间，再汇总成每个 symbol 的历史特征。**

这一项回答的是“过去是否出现过极强、极集中、反复发生的上涨表现”，不是“当前是否值得买”。历史标签不等于未来预测能力，是否应该给综合 score 加分，还需要后续验证。本次只讨论定义，不查询具体名单、不运行数据、不声称已有验证结果。

#### 1. 与另外两个维度分开

| 维度 | 主要回答的问题 | 边界 |
|---|---|---|
| 历史异常强势 | 过去是否出现过异常强势表现，强到什么程度、发生过几轮 | 形成历史记忆特征，不直接评价当前机会 |
| 活跃度 | 近期成交、换手等是否活跃 | 不把当前放量重复算进历史标签 |
| 近期 K 线 | 最近处于什么价格结构 | 不因近期刚涨起来，就同时获得高额历史加分 |

建议把这一项在实现层命名为“历史异常强势特征”。名称背后应有统一计算规则，不依赖新闻称呼或人工印象。

#### 2. 识别两类，而不是只看连板

**A 类：连板爆发型。** 在较短时间内连续触及 lmt_up，或者多次触及 lmt_up 并伴随明显的区间 chg。

- 核心指标：最长连续 lmt_up 天数、固定窗口内 lmt_up 次数、同窗口累计 chg。
- “连续”按统一交易日历判断，停牌不能把两段 lmt_up 拼成一段连续 lmt_up。
- 单独记录 flat 比例。它能说明表现极端，但不代表历史上可实际 buy。

**B 类：快速大幅 chg 型。** 不一定连续 lmt_up，但短期累计 chg 非常突出。

- 核心指标：多个固定窗口累计 chg，以及相对同期可比对象的 chg 分位。
- 同时观察相对 markt 的超额表现，避免把普遍 chg 中的普通强势误认为异常。
- 不只看长期从最低 px 到最高 px 的倍数。起止点任意挑选，很容易把缓慢上行或事后挑出的完美区间混进来。

建议初版保留两类标签，不急着合成一个“是/否”。如果只关注连板型，可以明确缩小范围。

#### 3. 怎么产生候选区间

建议采用“固定窗口扫描 → 异常条件触发 → 相邻命中合并”的流程：

1. **逐日扫描**：只用当日及之前的数据计算指标，不拿后来的最高点倒推当时就应知道的标签。
2. **分两条路径触发**：连板路径看连续 lmt_up 强度；快速 chg 路径要求“绝对 chg 门槛”与“同组相对强度门槛”同时满足。
3. **合并重复命中**：同一轮上行可能连续多天触发，也可能同时命中多个窗口或两种类型，应保留一次事件及多个类型标签，不计为多轮。
4. **记录首次识别日**：首次达到条件的日期，就是该标签最早可用的时点。其后如果强度继续增加，只能从后续时点更新，不能倒填回首次识别日。
5. **谨慎确定结束日**：若要靠后续回落或冷却间隔确认一轮结束，必须另记“结束确认日”；在确认前标为进行中，不使用事后峰值和最终持续时间。

初版可先把 **5、10、20 个交易日**作为候选扫描窗口，把**近 3 年**作为候选回看范围；这些只是设计起点，不是已证明有效的参数。chg、lmt_up、分位门槛及相邻区间合并间隔应在检查真实数据覆盖与分布后再定，不先拍定一个通用数字。

#### 4. 比较前先统一口径

| 问题 | 建议处理 |
|---|---|
| 不同涨跌幅制度导致连板不可直接比较 | 按当日实际适用制度分组；保存连板天数与实际累计 chg，不直接把不同制度下相同板数视为同等强度 |
| lmt_up 识别 | 优先使用可核验的当日 lmt_up px 或历史状态；不能统一用“chg 大于某个固定百分比”替代 |
| 上市初期、无涨跌幅限制日期及风险警示状态 | 按历史当时状态标记，初版建议单列，不混入常规组；这些阶段不能被误判为普通 lmt_up 日 |
| 除权除息影响区间 chg | 用同一可追溯 adj 口径计算 chg；lmt_up 判断仍使用当日未 adj px 及对应 lmt_up px |
| 停牌或数据缺失 | 停牌与缺记录分开处理；不可计算的窗口标记未知，不能当作零 chg 或未命中 |
| 历史长度不足 | 单独标记覆盖天数及覆盖不足，不把“没观察到”解释成“从未发生” |
| 幸存者偏差 | 在历史评价日使用当时的 symbol 范围，包括后来 dl 的对象，不能只用今天仍在的名单回看 |

以上是需要满足的数据条件，不代表已核实本项目数据源具备全部字段。

#### 5. 最终给每个 symbol 保留什么

先保留可解释的原始特征，比马上凑一个总 score 更有价值：

| 特征 | 含义 |
|---|---|
| 是否出现过历史异常强势区间 | 区分“有”“未观察到”“数据不足”，后两者不要混为一谈 |
| 历史类型 | 连板爆发型、快速 chg 型，允许同时具备 |
| 最强一次的强度 | 保留窗口、chg、可比组分位、连板天数，不只存单个标签 |
| 独立发生次数 | 合并同一轮的重复触发后，统计真实不同轮次 |
| 最近一次距今多久 | 表达历史记忆的新旧程度 |
| 历史数据覆盖 | 防止历史短的 symbol 因样本少而被误判 |
| flat 比例等附加状态 | 描述表现特征与可成交性差异，不直接等同于加分 |

若后续需要形成 score，可以再考虑“最强强度＋重复发生能力＋时间衰减”，但**初版不预设权重，也不默认越极端越应该加分**。极端上行历史也可能伴随较高波动和 dd，应把风险特征与正向特征分别保存。

#### 6. 我更推荐的初版范围

- 为避免和近期活跃度、近期 K 线重复，建议划出独立的近期窗口：例如评价日之前最近 20 个交易日归入近期维度，历史维度只使用截至该窗口之前已知的信息。

## 根据用户回复整理后的已确认接口方向

### 1. 输入

历史异常强势识别接口接收 `preprocessing/factors.py` 已返回的 symbol 集合或对应查询结果，不再在评分模块内重新人工构造历史对象名单。

输入对象至少需要能够确定：

- `symbol`
- 历史大涨查询得到的候选身份
- 需要计算区间明细的评价范围
- 日 K 数据查询所需的日期范围

历史大涨查询与区间明细计算分为两个职责：前者负责提供候选 symbol，后者负责从日 K 表数据计算候选 symbol 的区间涨幅明细。

### 2. 类型判别

接口同时支持两类历史异常强势：

- 连板爆发型
- 快速上涨型

接口输出中必须保留类型字段，不能只输出一个合并后的布尔值。一个 symbol 可以同时属于两类，也可以只属于其中一类；无法判别时应保留未知状态，不把未知当作未命中。

类型判别所需的原始证据应与区间明细一起保留，至少能回溯到：

- 区间起止日期
- 起止 px
- 区间涨幅或倍数
- 区间内 lmt_up 相关统计（若数据源具备）
- 区间长度
- 有效日数量与缺失日数量
- 类型判别状态及原因

### 3. 区间涨幅明细

对于每一个输入 symbol，接口从日 K 表数据计算并输出区间涨幅明细。首版应优先复用 `find_doubling_symbols` 已有的区间计算结果结构，不在评分模块另写一套相同的区间扫描逻辑。

现有结果字段可作为基础字段：

| 字段 | 作用 |
|---|---|
| `ts_code` | symbol 身份 |
| `start_date` / `end_date` | 区间边界 |
| `start_close` / `end_close` | 区间起止 px |
| `multiple` | 区间倍数 |
| `calendar_days` | 日历位置跨度 |
| `valid_close_days` | 有效 px 天数 |
| `missing_close_days` | 区间内缺失 px 天数 |

后续为支持类型判别，再补充或关联以下信息：

- `event_type`：`streak`、`fast_gain` 或多类型集合
- `lmt_up_days`：区间内 lmt_up 天数；字段可用性需先核对
- `max_streak`：区间内最长连续 lmt_up 天数；字段可用性需先核对
- `relative_rank`：相对同期可比对象的强度分位；暂不作为接口已实现字段
- `status`：`confirmed`、`unknown`、`insufficient_data` 等状态
- `status_reason`：无法判别或数据不足的原因

以上新增字段是接口设计方向。其中只有现有区间字段可视为已有实现基础，新增字段不能在未修改接口和未用真实数据验证前宣称已经输出。

### 4. 评分模块的边界

- `preprocessing/factors.py`：查询历史大涨候选并提供候选输入；负责区间扫描基础能力。
- 评分模块：接收候选输入，组织并输出每个 symbol 的区间涨幅明细及类型判别结果。
- 综合 score：暂不根据历史异常强势直接设定权重，也不把类型判别直接转换为最终分值。

### 5. 当前已确认与未确认

**已确认：**

- 两类历史异常强势都纳入：连板爆发型、快速上涨型。
- 候选 symbol 来自 `preprocessing/factors.py` 的历史大涨查询返回值。
- 评分侧需要输出每个 symbol 的区间涨幅明细。
- 区间明细从日 K 表数据获得。
- 接口方向已经确定，后续围绕接口实现和字段完整性推进。

**仍需在实现前核对：**

- 现有候选返回值的准确字段名与数据结构。
- 连板爆发型的判别字段是否已经在现有查询结果中，还是需要额外从日 K 表计算。
- 快速上涨型的具体判别门槛。
- 多个重叠区间如何合并，以及 `cooldown_days` 的最终口径。
- 相对同期强度是否首版实现，还是先仅输出绝对区间明细。
- 评分模块最终接收 DataFrame、symbol 列表，还是结构化结果对象。

## 对新问题的回复（2026-09-22）

### 一、先确定数据边界

根据当前数据接口说明，首版可以稳定取得：

- 每个 symbol 的 `trade_date`、`open`、`high`、`low`、`close`；
- `find_doubling_symbols` 已返回的区间起止日期、起止 close、倍数、统一日历跨度、有效 close 天数和缺失 close 天数；
- `get_events` 可取得 `zt`、`dt`、`zb`，但它不是完整历史 lmt_up 来源，不能把“异动表无记录”解释为“当日没有 lmt_up”。

因此，**历史类型判别的主来源仍应是日 K 数据**。其中：

- 快速上涨型可以直接建立在已有区间倍数结果上；
- 连板爆发型需要根据日 K 的前收盘、当日适用限制比例和价格最小单位自行判别；
- `get_events` 仅作为抽样校验或补充证据，不作为历史全量判别的唯一来源。

当前接口文档还明确：日 K 查询不会自动补缺失日期，缺失 close 不应补零或前向填充。因此类型判别必须区分“未命中”和“数据不足”。

### 二、连板爆发型：建议定义

#### 1. 定义目标

连板爆发型不是单纯“区间涨幅很大”，而是：

> 在较短的统一交易日序列内，连续多个交易日达到各自当日的 lmt_up 条件，并形成可识别的集中爆发区间。

这里的“连续”指统一交易日历上的连续交易日，不是某个 symbol 自身有记录的连续日期。停牌或缺失记录不能被压缩后当作连续。

#### 2. 单日 lmt_up 判别

对每个 symbol、每个交易日计算：

```text
prev_close = 该 symbol 之前最近一条有效 close
limit_px = round(prev_close * limit_ratio, 2)
is_lmt_up = close >= limit_px
```

其中 `limit_ratio` 不能永久写死为单一常数，至少应由以下信息决定：

- 当日所属板类别；
- 当日是否处于上市初期无限制阶段；
- 当日风险状态及其他限制比例变化；
- 是否存在有效前收盘。

如果当前数据源无法提供历史状态和限制比例，首版应明确采用“主板普通状态固定比例”的受限口径，并在结果中记录 `limit_rule_status`，不能把它描述为所有历史日期的真实 lmt_up 状态。

为避免浮点误差，比较前统一按最小 px 单位处理；不要用“涨幅大于某个百分比”替代限制 px 比较。

#### 3. 事件级判别

建议先按日生成 `is_lmt_up`，再在每个 symbol 内扫描候选区间。首版建议同时保留以下三层字段：

| 层级 | 建议字段 | 作用 |
|---|---|---|
| 单日 | `is_lmt_up`、`limit_rule_status` | 说明当天是否可判别及判别依据 |
| 连续段 | `streak_start_date`、`streak_end_date`、`streak_days` | 记录连续 lmt_up 段 |
| 区间汇总 | `lmt_up_days`、`max_streak`、`streak_density` | 支持最终类型判别 |

**推荐的初版触发条件：**

- `max_streak >= 3`：识别为连板爆发候选；
- 若连续段不足 3 天，但在 10 个交易日内 `lmt_up_days >= 4`，同时区间累计 chg 达到候选门槛，也保留为连板爆发候选；
- 若一个区间同时满足快速上涨条件，则 `event_type` 同时保留 `streak` 和 `fast_gain`，不强行二选一。

这里的 3、4、10 只是首版可配置起点，不是经过真实数据验证后的最终阈值。接口应把它们作为参数或配置记录，不写成散落在代码中的隐含常数。

#### 4. 为什么不只用连续 3 日

只用最长连续段会漏掉以下情况：

- 中间出现一次非 lmt_up，但整体仍是短期密集爆发；
- 因限制比例变化或价格精度导致某一天未达到计算条件，但区间整体强度明显；
- 多个短连续段在同一轮上行中密集出现。

所以建议保留“最长连续段”和“窗口内 lmt_up 密度”两个证据，不把任意一个字段直接当作最终分值。

### 三、快速上涨型：建议定义

#### 1. 定义目标

快速上涨型关注的是固定窗口内的区间强度，而不是是否连续 lmt_up：

> 在预先规定的交易日窗口内，symbol 的 close 从区间起点到终点达到明显倍数或 chg 门槛，且区间边界由当时可用数据确定。

这与已有 `find_doubling_symbols` 的职责高度一致，因此不建议在评分模块重复写另一套最低 close 扫描。

#### 2. 首版建议直接复用已有区间候选

首版可定义为：

```text
fast_gain_candidate = find_doubling_symbols 的有效区间记录
```

现有默认示例是 `window=60`、`threshold=2.0`，但这只是当前函数调用参数，不应自动被解释为已确认的类型判别口径。建议接口把以下参数显式带入结果属性或配置：

- `window`
- `threshold`
- `cooldown_days`
- `price_field`
- `calendar_source`

#### 3. 快速上涨的类型字段

建议使用以下判断：

- 区间记录有效、倍数达到指定阈值、缺失状态不阻断 → `fast_gain`；
- 区间倍数达到阈值，但缺失 close 或统一日历不足以确认完整窗口 → `unknown` 或 `insufficient_data`，不能直接标记 `fast_gain`；
- 区间不存在有效触发记录 → `not_detected`，不等于“历史上从未发生”。

快速上涨型不要求 `max_streak` 达到连板门槛；如果同时满足连板条件，则保留两个类型标签。

### 四、两类定义如何合并

我建议 `event_type` 不设计成互斥枚举，而设计成可多值字段：

```text

["fast_gain"]

```

同时增加整体状态字段：

```text

not_detected
unknown
insufficient_data
```

这样可以避免把以下情况混在一起：

- 没有触发任一条件；
- 数据不足，无法判别；
- 已触发快速上涨，但没有连板证据；
- 同一轮同时具备两类特征。

### 对评分问题的回复（2026-09-22，建议方案，待确认）

#### 一、先区分“类型识别”和“评分”

两类类型只能回答“历史上发生过哪一种强势表现”，不能直接决定分数。评分应建立在可解释的原始特征之上，而不是把 `streak` 和 `fast_gain` 简单编码成 0/1 后相加。

建议保留三层结构：

1. **事件明细层**：保存每个区间的原始证据，例如区间长度、倍数、`lmt_up` 天数、最长 `streak`、数据完整性和距离评价日的时间。
2. **类型子分数层**：分别计算 `streak_score` 与 `fast_gain_score`，保证两类特征可以单独分析。
3. **历史总分层**：在明确两类分数的含义后，再决定合成方式；不能让合成分数掩盖类型差异。

这样可以回答三个不同问题：是否命中过、哪一类更强、历史信息整体是否值得进入综合 `score`。

#### 二、建议的初版评分结构

##### 1. 事件明细先做单调变换

每个事件不直接使用原始值，而是把强度、重复性和新旧程度拆开：

```text
intensity_score   = 区间强度的截面 Rank
repeat_score      = 独立事件次数的截面 Rank
recency_score     = 时间衰减后的 Rank
quality_score     = 数据完整性与规则可判别性的质量分
```

其中 `Rank` 是同一评价日内的截面分位或百分位，不建议直接比较原始倍数。质量分不应伪装成强度分：数据不足时应标记为 `unknown` 或 `insufficient_data`，而不是通过降低分数来表示。

##### 2. `streak` 类型子分数

建议先把每个独立区间转为事件分数：

```text
streak_event_score =
    0.50 * rank(max_streak)
  + 0.25 * rank(lmt_up_density)
  + 0.15 * rank(repeat_score)
  + 0.10 * rank(recency_score)
```

再按 symbol 汇总：

```text
streak_score = max(confirmed streak_event_score)
```

这里使用 `max` 的含义是保留历史上最强的一次 `streak` 记忆，避免同一轮事件因多个重叠区间重复加分。若后续发现重复发生本身具有独立解释力，可另加一个有上限的重复项，但不建议首版同时把事件次数和多个重叠区间全部累加。

##### 3. `fast_gain` 类型子分数

快速上涨型更适合强调区间强度，同时保留重复发生和时间衰减：

```text
fast_gain_event_score =
    0.50 * rank(multiple)
  + 0.25 * rank(relative_strength)
  + 0.15 * rank(repeat_score)
  + 0.10 * rank(recency_score)
```

其中 `relative_strength` 如果首版尚未实现，可以暂时不放入正式分数，而改为：

```text
fast_gain_event_score =
    0.60 * rank(multiple)
  + 0.25 * rank(repeat_score)
  + 0.15 * rank(recency_score)
```

此处必须在配置中明确 `window`、`threshold` 和缺失数据处理方式。不同窗口得到的事件不能在未标准化前直接相加。

##### 4. 历史总分的暂定合成

建议首版不要使用两类分数的加权和，而先使用：

```text
history_score = max(streak_score, fast_gain_score)
```

理由是：两类表示不同的历史强势路径，直接相加容易让同时命中的 symbol 获得重复奖励，也无法判断高分来自哪一类。输出中同时保留：

```text
history_score
streak_score
fast_gain_score
history_type
history_status
```

如果后续真实数据验证表明“两类同时具备”有稳定的增量解释力，再把交集作为单独的 `type_bonus`，而不是简单叠加两套完整分数：

```text
history_score = max(streak_score, fast_gain_score) + type_bonus
```

`type_bonus` 应设置上限，并且必须通过样本外检验后才允许进入正式综合 `score`。

#### 三、为什么建议使用 Rank，而不是直接使用原始值

原始倍数、`streak` 长度和事件次数的量纲不同，且通常存在长尾。直接相加会导致极少数极端事件支配结果。截面 `Rank` 有三个优点：

- 把不同量纲转成可比较的 0 到 1 区间；
- 降低极端值对总分的支配；
- 便于按评价日做横截面比较，并与后续 `RankIC`、分层检验保持一致。

建议在正式计算前明确以下细节：

- 同分值使用平均秩；
- 只在同一评价日、同一可比范围内标准化；
- 数据不足与未命中分开编码；
- 若要跨时期比较，再保存标准化版本和原始版本；
- `Rank` 只处理排序，不替代缺失值规则。

#### 四、状态和分数必须分开

建议不要用 0 分同时表示“未命中”“数据不足”和“确实弱”。至少保留：

```text
history_status = confirmed / not_detected / unknown / insufficient_data
score_value     = 有效时的数值，否则为空
score_source    = streak / fast_gain / both
```

推荐解释：

- `confirmed`：满足类型条件，且所需数据足够；
- `not_detected`：在已覆盖且可判别的范围内未触发；
- `unknown`：存在规则或字段不确定，不能可靠判断；
- `insufficient_data`：历史覆盖或区间数据不足。

对于 `unknown` 与 `insufficient_data`，首版不建议自动给负分。是否剔除、缩尾或使用中性值，应由上层截面流程另行规定。

#### 五、评分依据如何验证

权重 `0.50 / 0.25 / 0.15 / 0.10` 只能作为可解释的起点，不能称为已证明的最优权重。建议按以下顺序验证：

1. **单因子方向检查**：分别检查 `max_streak`、`multiple`、事件次数和新旧程度与未来目标的单调关系。
2. **RankIC**：按评价日计算历史特征与未来目标的截面秩相关，并报告均值、标准差、ICIR 和有效日期数。
3. **分层检验**：按 `history_score` 分为若干层，比较各层未来目标的均值、风险和稳定性。
4. **增量检验**：控制近期 `chg`、活跃度、`sector` 和 `markt` 状态，观察历史分数是否仍有增量解释力。
5. **样本外检验**：按时间划分开发期、验证期和样本外期，权重只能在开发期确定。
6. **稳定性检验**：改变窗口、阈值、衰减速度和分层数量，观察结论是否对轻微参数变化敏感。

若只在同一段历史上反复选择权重，会产生多重检验偏差。因此每一次权重或阈值调整都应保留配置差异和验证结果，不能只报告最好的版本。
